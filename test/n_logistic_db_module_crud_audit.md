# N Logistic Database — Module-wise CRUD Audit and Fix Notes

## Result

The uploaded master SQL contains 28 core tables, 6 SQL views, 4 triggers and 9 stored procedures. It does **not** contain a complete module-wise set of CRUD statements or Java DAO implementations. The 6 existing views are reporting/join views, not proof that each module's UI can view, update or delete records.

The SRS specifies Java MVC2, JDBC/PreparedStatement and DAO access. Therefore:

- SQL tables, keys, views, triggers and procedures belong in the database script.
- Create/read/update/delete methods belong in the relevant Java DAO and are called by Servlets/Services.
- Delete must follow the business meaning. Deactivate master data, cancel bookings, preserve movements, and retain financial/audit history.

## Module operation matrix

| Module | Create | View / Read | Update | Delete policy |
|---|---|---|---|---|
| Users | Register user | User list/detail | Profile, role, status | Deactivate (`INACTIVE`), do not erase account history |

| Vessels | Add vessel | Vessel list/detail | Details and `ACTIVE` / `MAINTENANCE` status | Deactivate; preserve shipment history |
| Containers | Add container | Available/all container list | Details and operational status | Delete only if never referenced; otherwise status workflow |
| Shipments / Booking | Confirm booking | Shipment list/detail | Status through movement events; cancellation | Cancel, never hard-delete a confirmed shipment |
| Shipment Items | Add goods/quantities to booking | Items by shipment | Edit only while booking is still open | No delete after confirmation; reverse/cancel the booking |
| Container Movements | Add movement event | Timeline/history | Append a correcting event; don't overwrite old events | No hard delete |
| Pricing Rules | Add rule | Active/inactive rules | Rates, dates, multipliers | Deactivate (`is_active=FALSE`); preserve pricing audit |

## SRS-driven gaps found in the original SQL

1. Ports have no `is_active` field even though FR1 requires deactivation.
2. Vessels have only `ACTIVE` / `MAINTENANCE`; a separate `is_active` flag is needed if deactivation is required without destroying history.
3. Product schema has unit weight but no unit volume. FR3.4 says cargo weight and volume are calculated from goods.
4. Stock has no reserved quantity, so booked quantities cannot be distinguished from available stock.
5. Shipment-to-invoice is described as 1:1, but `billing_invoices.shipment_id` is not unique in the original SQL.
6. Only six report/join SQL views exist. They do not cover the individual list/detail screens for users, ports, vessels, containers, products, pricing and claims.
7. The original payment trigger recalculates invoice status only on payment INSERT, not payment UPDATE/DELETE.
8. `claim_comments` is missing even though FR7.7 says both parties can add comments.
9. `claim_items` is missing, so the DB cannot identify which stock/product quantities a settled loss/damage claim should adjust.
10. `tax_rates` configuration is missing for FR5.2.
11. SRS 3.8.3 and 3.9.3 specify `ai_chat_log`, `ai_claim_summaries`, `ml_predictions` and `anomaly_alerts`; they are not in the original 28 core tables/ERD.
12. Shipment stock reservation and automatic invoice creation need to be run in the booking transaction. The original SQL did not supply a complete booking confirmation operation.
13. Pricing audit originally records only some rate fields, not all weight/volume rates and both multipliers.
14. Claim settlement originally updated an existing P&L row only and did not create the row when absent or adjust affected inventory.

## Files prepared

- `n_logistic_db_srs_extension_patch.sql`: one-time SQL extension for the missing supporting columns/tables, module read views, payment resynchronization, booking stock reservation/invoice helpers, pricing/claim audit improvements and settlement support.
- `n_logistic_db_module_crud_reference.sql`: parameterized SQL examples for module Create/View/Update/Delete policies and a DAO method checklist.

## Important implementation boundary

The SQL files do not implement the Java UI. To verify that the professor's CRUD requirement is fully met, each Java module must have corresponding DAO methods and Servlet/Service actions. The companion CRUD SQL file is the SQL contract those DAOs should use. The Java source files were not part of the uploaded materials, so actual JSP/Servlet buttons, route handlers and DAO method implementations cannot be certified from the SQL files alone.

## Apply / verify sequence

1. Back up `n_logistic_db`.
2. Run the original master SQL on a test database.
3. Check `billing_invoices` for duplicate `shipment_id` values; resolve duplicates before the unique key is added.
4. Run `n_logistic_db_srs_extension_patch.sql` once.
5. Run the POST-PATCH CHECKS at its end and inspect any rows returned by the duplicate-invoice or invalid-stock checks.
6. Implement/verify the DAO methods listed in `n_logistic_db_module_crud_reference.sql` with `PreparedStatement` and role/ownership validation in the Service layer.
7. Test all FR1–FR7 acceptance flows, especially over-capacity booking, unavailable container, stock reservation, partial/full payment, claim settlement, and shipment timeline.

The patch preserves the 28 original core tables but adds 10 supporting tables. If your professor requires the ERD to show every physical table, update the ERD to include these support tables; do not silently label the expanded schema as exactly 28 tables. The patch is a static SQL deliverable and has not been executed against the user's XAMPP/MySQL instance. Test it on a copy before applying it to the project database.
